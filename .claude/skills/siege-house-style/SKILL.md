# Siege game house style (gunmodls)

The repo holds procedural assets for an original Rainbow-Six-Siege-like 5v5 attack/defend shooter.
Everything is ORIGINAL: no real brands, logos, emblems or copied game designs. Read the asset's own
README / INTEGRATION.md / DESIGN.md before touching it.

## 1. World and look
- Setting: 2111 near-future Seoul, rainy night, purple-neon city. Map: Haneul Tower (96F-98F of a
  fictional supertall). Korean identity without text: changsal lattice, hanji panels, stone, warm wood,
  celadon, indigo / cinnabar / ochre accents under purple neon.
- **House palette:** dark alloy / graphite / near-black fabric, with small **purple #8a4dff** accents
  (a strip, a few status dots). Purple is sparse: never on traditional pieces, never flooding a model.
  Warm secondary accents (bronze, brass, amber) are fine when the reference calls for them.
- **No text anywhere:** no letters, digits, Hangul, pseudo-script, logos or emblems in geometry or
  textures. Screens show abstract light fields, pictograms and UI shapes only (screen atlases).
- **Realism bar ("not AI slop"):** real proportions and real-world dimensions in metres, believable
  construction (seams, fasteners, hinges, webbing widths, vents, cable management), clean bevels, no
  floating or intersecting parts, deliberate silhouettes, subtle wear. Compare with real references.
- Sci-fi gadgets look like plausible hardware: rugged housings, TPU/rubber overmoulds, Torx screws,
  status LEDs, vents, not glowing toy shapes.

## 3. Gadget conventions (Siege-style)
- Every gadget is a game ability: it has a clear deploy -> active -> idle/destroyed lifecycle, readable
  states (LED colours, screen cells, sounds) and counterplay. Write it into README/INTEGRATION.
- Animation clips in the GLB (typical: `deploy`, `idle`, `active`/`fire`, `destroyed`/`eject`), named
  locator empties for gameplay (`muzzle`, `fx_*`, `grip_attach`, `screen_center`, sensor origins).
- Screens use a texture ATLAS (cells for boot, idle, states, error) swapped by UV offset from the Unity
  script; pictograms only.
- Sounds: procedural WAVs in `sounds/` generated by a script, plus a `sounds.js` for the viewer.
- Unity script per gadget (MonoBehaviour): public methods for the game (Deploy, Activate, Destroy...),
  UnityEvents for game logic, clip playback (legacy Animation or Animator), LED/screen switching,
  cooldowns, gizmos. Compile-check with mcs against stubs; say it is not run in Unity.
- Operator gadgets pair with operators (e.g. Nox -> tracker tags, N1CK -> nullfield) and must be able
  to talk to each other where the design says so (e.g. sensors ask `Nullfield.IsHidden`).

## 4. Map rules (Haneul Tower)
- Surfaces are typed: hard (indestructible: core, columns, slabs, every wall corner and T-junction for
  1.0 m along each arm), breakable + reinforceable (every breakable wall can be reinforced), hatches,
  glass, barricades, open slots. Keep destructible walls large; no thin breakable strips.
- Blast shutters on outer room facade bays (open by default), none on bays with a door.
- Stairs are real stairs (no one-way gaps); spiral stair replaced by a hatch.
- After any change: `python3 tools/build_layout.py && python3 tools/validate_layout.py` (0 errors),
  render plans, navtime. Port hand edits back into the generator.
- Furniture is placed by the user, never baked into the map. Pieces follow the furniture contract in
  the pack's DESIGN: origin on the floor at footprint centre, front +Z, named parts that detach or
  shatter, pre-cut chunks at scale 1e-4, `col_*` proxies, cover class (none / soft / hard).

## 5. Pipelines
- **three.js procedural** (guns, gadgets, furniture, phone/tablet): parts in JS, `assemble.sh` +
  `standalone.py` produce `viewer.html`; three.js r0.180.0; viewer debug contract
  `window.__model = {id, ready, exportScenes, exportGLB, debug}`; export with
  `node tools/export-glb.js --out ...`; Unity copy with `node tools/unity-export.js <glb>` (merged meshes,
  UV0 box projection, LOD0/1/2, `_COL` boxes); `node tools/check-glb.js`.
- **Blender bpy** (characters, organic shapes, rigs): `scratchpad/human/venv/bin/python`; no GL, so
  Cycles with low samples + denoise. Gotchas: `bpy.context.view_layer.update()` before setting
  `matrix_parent_inverse`; cameras via `to_track_quat('-Z','Y')`; give every exported part UVs.
- Validation: Khronos glTF validator must report 0 errors. Headless Playwright screenshots: route
  `cdn.jsdelivr.net` to local node_modules, abort other external requests, test 1280 px and 390 px.
- Looks are judged by rendering and LOOKING: hero 3/4, front/back/sides, close-ups, and at gameplay size.

## 6. Delivery checklist (per asset)
`<id>.glb`, `unity/<id>.glb`, `viewer.html`, `preview.png`, `README.md` (what it is, parts, clips,
sizes, triangles, known weaknesses), `INTEGRATION.md` (Unity setup), `unity/Runtime/<Asset>.cs`,
sounds if any. Add a row to the root README table, a preview line, the Unity sentence, and an entry in
`index.html`; add the viewer to the gallery artifact. Ship to `main` from a detached worktree; commits
authored as ThatsALotOfBees2 (email from `git log -1 --format=%ae`).

## 7. Working lessons
- The owner's usage limit is tight: build small things directly, use at most a builder + reviewer +
  fixer for bigger ones, never four heavy builds at once, keep prompts and outputs lean.
- Workflow sub-agents latch onto the latest chat message: give every prompt an explicit intent/scope
  note saying chat messages like "status?" or "pics?" do not change the task.
- Send progress pictures when asked; be honest about what is unverified (nothing is run in Unity here).
- When the user says "quick fixes, don't overcomplicate", do exactly that.
